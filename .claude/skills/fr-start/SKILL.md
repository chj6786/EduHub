# 요구사항 착수: $ARGUMENTS

이 스킬은 **분석·설계·계획만** 한다. 쓰는 파일은 다음 두 개뿐이다. 그 밖의 파일(코드, 설정, 마이그레이션)은 만들거나 고치지 않는다.

- 설계 명세: `docs/design/<ID>.md` (예: `docs/design/FR-04.md`)
- 구현 계획: `docs/plans/<ID>.md` (예: `docs/plans/FR-04.md`)

승인은 **두 번** 받는다. 설계 명세 승인 → 구현 계획 작성 → 구현 계획 승인. 구현은 두 번째 승인 뒤에 시작한다.

같은 ID의 파일이 이미 있으면 덮어쓰지 말고, 내용을 보여 준 뒤 이어서 고칠지 새로 쓸지 사용자에게 묻는다.

## 1. 분석

- `docs/requirements.md`에서 해당 요구사항을 찾아 다음을 읽는다:
  - 요구사항 행
  - 관련 NFR
  - "결정 사항"(D-xx)
- 관련 코드를 읽는다. 대상은 도메인 패키지, 기존 엔티티, Flyway 마이그레이션, 컨트롤러 패턴이다.
- 요구사항이 애매한 부분은 질문으로 정리한다. 최대 5개까지만 적는다.

## 2. 설계 명세 → `docs/design/<ID>.md`

아래 항목을 표나 목록으로 쓴다.

- **범위**: 이번에 하는 것과 하지 않는 것
- **API**: 메서드, 경로, 요청·응답 DTO, 상태 코드(400, 404, 409 등)
- **데이터**: 테이블과 컬럼 변경, 제약(유니크, 부분 인덱스), 다음 마이그레이션 번호 `V{n}`
  - 중복을 막아야 하는 곳은 DB 유일 제약으로 보장하고, 제약 위반을 409로 바꾸는 방법을 적는다.
- **트랜잭션과 동시성**:
  - 트랜잭션 경계
  - 락 대상과 순서
  - NFR-01에 해당하는지
- **보안**: 인증과 본인 확인이 필요한 곳(NFR-03). 아직 없으면 `TODO(NFR-03)`으로 표시한다.
- **테스트 시나리오**:
  - 단위 테스트
  - 슬라이스 테스트
  - 동시성 테스트(해당 시)
- **열린 질문**: 1단계에서 정리한 질문

파일을 쓴 뒤 요약과 열린 질문을 보여 주고, **설계 명세 승인을 요청하며 멈춘다.** 사용자가 고칠 점을 말하면 명세 파일을 고치고 다시 승인을 요청한다.

## 3. 구현 계획 → `docs/plans/<ID>.md`

설계 명세가 승인된 뒤에만 쓴다. 파일 맨 위에 설계 명세 경로를 적는다.

- 작업을 T1, T2, …로 나눈다. 각 작업은 한 번 리뷰할 수 있는 크기로 한다.
- 작업마다 다음을 적는다:
  - 바꿀 파일
  - 완료 기준
  - 확인 명령(예: `./gradlew test --tests "*XxxTest*"`)
- 순서 의존이 있으면 표시한다.
- 루트 `CLAUDE.md`의 확대 보고 기준(파일 3개 이상, 여러 계층, diff 1,000줄 이상)에 걸리는 작업은 표시하고, 나눌 수 있으면 나눈다.

## 4. 마무리

계획을 요약해 보여 주고, **구현 계획 승인을 요청하며 멈춘다.** 승인 전에는 implementer를 부르지 않는다.
